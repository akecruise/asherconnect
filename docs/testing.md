# วิธีจำลอง scenario ในการทดสอบ

เอกสารนี้ไม่ได้อธิบายว่า "มีเทสต์อะไรบ้าง" (ดูที่ `npm test`) แต่อธิบายว่า
**จะจำลองสถานการณ์หนึ่งขึ้นมาทดสอบได้อย่างไร** — เพื่อให้คนต่อไปเพิ่มฉากใหม่ได้
โดยไม่ต้องคิดวิธีเองใหม่ทุกครั้ง และไม่เผลอเขียนเทสต์ที่ผ่านแบบไม่มีความหมาย

## 1. กติกา 6 ข้อที่ทุกฉากต้องเคารพ

| # | กติกา | ถ้าไม่ทำแล้วเกิดอะไร |
|---|-------|----------------------|
| 1 | **คุมเวลา อย่ารอเวลา** — ป้อน `p_now` เข้าไปเอง | กฎ "เงียบเกิน 24 ชม." / "นอกเวลาทำการ" จะทดสอบไม่ได้เลย ต้องรอของจริง |
| 2 | **คุมการสุ่ม** — ป้อน `p_jitter = 0` | ตัวเลขวินาทีเทียบไม่ได้ เทสต์จะผ่านบ้างไม่ผ่านบ้าง |
| 3 | **คุมโลกภายนอก** — ส่ง `fetcher` ปลอมเข้าไปทาง argument | เทสต์ยิง Claude/Meta จริง = เสียเงิน ช้า และพังตอนเน็ตล่ม |

| 6 | **ฉากต้องเก็บกวาดตัวเอง และมีข้อพิสูจน์ว่าสะอาด** | ฐานทดสอบสกปรกขึ้นทุกวัน สุดท้ายเทสต์ชนกันเอง |

## 3. แบบ A — ฉากเป็นข้อมูล ไม่ใช่โค้ด

ใช้เมื่อ: ตรรกะเป็นฟังก์ชันบริสุทธิ์ (input → output) เช่น ตอบไหม / แจ้งทีมไหม / หน่วงกี่วินาที

**วิธีจำลอง** — เขียนฉากเป็น "ประโยคสั้น ๆ" แล้วมีตัวแปลประโยคเป็น context

```js
// tests/decide.test.mjs
const at = (hour, minute) => `2026-01-01 ${pad(hour)}:${pad(minute)}:00+07`

// ฉากหนึ่ง = คำสั้น ๆ ชุดหนึ่ง — parseSim() แปลเป็น ctx ให้
['09:00', 'ใหม่', 'ราคาเท่าไหร่']        // → ตอบทันที
['08:59', 'ใหม่']                        // → นอกเวลา ยังไม่ตอบ
['เดิม', 'คนตอบ5']                       // → คนเพิ่งตอบ บอทต้องเงียบ
```

ข้อดีที่สำคัญที่สุด: **เพิ่มฉากใหม่ = เพิ่มหนึ่งบรรทัด** ไม่ต้องเขียนเทสต์ใหม่ทั้งก้อน
คนที่ไม่ใช่โปรแกรมเมอร์อ่านรายการฉากแล้วบอกได้ว่าตกฉากไหน

**วันที่ตายตัว `2026-01-01`** — วันไม่มีผลต่อตรรกะ มีแต่ชั่วโมงกับนาที
การตรึงวันไว้ทำให้ผลเหมือนเดิมทุกครั้ง ไม่ว่าจะรันวันไหน

**จุดที่เคยพลาด** — 29 ฉากนี้ป้อน `phone_in_text` เข้า ctx โดยตรง จึงไม่เคยเดินผ่าน
`inbox.extract_phone()` เลย ตัวดึงเบอร์จึงพังอยู่หลายเดือนโดยที่ 29 ข้อเขียว
👉 **บทเรียน: ถ้าฉากป้อนค่าที่ระบบจริงต้องคำนวณเอง ต้องมีอีกชั้นที่ทดสอบตัวคำนวณนั้นด้วย**

## 4. แบบ B — ฉีดตัวปลอมแทนโลกภายนอก

ใช้เมื่อ: โค้ดต้องเรียก Claude, Meta, LINE, Telegram

**หลัก: `fetch` ต้องเป็น argument เสมอ ไม่ใช่ของ global ที่เรียกตรง ๆ**
ถ้าโค้ดเรียก `fetch` เองไม่มีทางจำลองได้ ต้องแก้โค้ดให้รับเข้ามา

```js
// tests/bots.test.mjs — ตัวปลอมของ Claude ที่จดด้วยว่าถูกเรียกด้วยอะไร
const claude = (text, status = 200) => {
  const seen = {}
  const fetcher = async (url, init) => {
    seen.url = url; seen.body = JSON.parse(init.body)
    return new Response(JSON.stringify({content:[{type:'text',text}]}), {status})
  }
  return { seen, fetcher }
}
```

`seen` สำคัญพอ ๆ กับค่าที่คืน — ทำให้ตรวจได้ว่า **ส่งอะไรออกไป** เช่น
prompt มีข้อมูลโครงการที่ถูกต้องไหม, มาสก์เบอร์ก่อนส่งออกไหม

**ฉากที่ต้องมีเสมอสำหรับทุกช่องทางภายนอก**

| ฉาก | ตัวปลอมคืนอะไร | ต้องได้ |
|-----|----------------|---------|
| ปกติ | 200 | `sent` |
| ปฏิเสธถาวร | 400 | `failed` — **ห้ามลองใหม่** |
| ติดลิมิต | 429 | `retry` |
| เน็ตหลุด | `throw` | `uncertain` — ไม่รู้ว่าถึงหรือไม่ ห้ามเดา |
| ยิงซ้ำ | 409 | `sent` + เอา id ที่ปลายทางเคยรับไว้ |
| หมดหน้าต่าง 24 ชม. | `throw new Error('must not call')` | `failed` **โดยไม่เรียกเลย** |

แถวสุดท้ายคือกติกาข้อ 5 — พิสูจน์ว่าบางกรณี **ต้องไม่มีการเรียกเกิดขึ้น**
ทำโดยใส่ตัวปลอมที่ระเบิดถ้าถูกเรียก

## 5. แบบ C — สร้างวันหนึ่งขึ้นมา แล้วนับสองทางให้ตรงกัน

ใช้เมื่อ: ผลลัพธ์เป็นตัวเลขที่ "ดูสมเหตุสมผล" ไม่พอ ต้องถูกจริง

**วิธี**: สร้างข้อมูลหนึ่งวันที่เรารู้คำตอบอยู่แล้ว แล้วเทียบ
1. `inbox.reply_report()` — คำนวณในฐาน (ของจริงที่จะใช้)
2. นับใหม่ด้วย JS จากแถวดิบ — **เขียนขึ้นใหม่อิสระในไฟล์เทสต์**

สองทางนี้ห้ามใช้โค้ดร่วมกันแม้แต่บรรทัดเดียว ถ้าใช้ร่วมกันก็แค่พิสูจน์ว่าโค้ดเท่ากับตัวมันเอง

**ฉากหนึ่งวันต้องมีอะไรบ้าง** — ครบทุกกรณีที่ทำให้สูตรแตกต่างกัน

- FB หนึ่งรอบ (มี echo → รู้ว่าใครตอบ)
- LINE หนึ่งรอบ (มี echo)
- **รอบค้าง** — ลูกค้าถามแล้วไม่มีใครตอบเลย
- **LINE fallback** — ไม่มี echo ต้องใช้ `last_human_reply_at` ผู้ตอบเป็น `unknown`
- **รอบข้ามวัน** — ถามเมื่อวาน ตอบวันนี้ (นี่คือเหตุผลที่ต้องมองย้อน 2 วัน)

ฉากข้ามวันคือฉากที่คนลืมบ่อยที่สุด และเป็นฉากที่ทำให้ตัวเลขเพี้ยนมากที่สุด

**ตอนที่สองทางไม่ตรงกัน** ให้ถือว่ายังไม่รู้ว่าใครผิด — ไปอ่านนิยามในสเปกก่อน
ครั้งหนึ่งทั้งสองทางตอบ 2 ตรงกันแต่ผมคาดไว้ 1 เพราะลืมว่ารอบข้ามวันก็เกิน 30 นาทีด้วย
👉 **ที่ผิดคือค่าที่ผมคาด ไม่ใช่ทั้งสองทาง** (กติกาข้อ 4 ทำงานตรงนี้)

## 6. แบบ D — หนึ่งบทสนทนาต่อหนึ่งผลลัพธ์

ใช้เมื่อ: ต้องพิสูจน์การจัดหมวด ที่มีลำดับความสำคัญทับกัน

**วิธี**: ตั้งชื่อฉากตามผลลัพธ์ที่อยากพิสูจน์ แล้วสร้างหนึ่งบทสนทนาต่อหนึ่งฉาก

```js
const CASES = {
  botOnly:   'บอทตอบ แล้วลูกค้าคุยต่อ',
  humanOnly: 'คนตอบ แล้วลูกค้าคุยต่อ',
  silent:    'ตอบแล้วลูกค้าเงียบ',
  none:      'ไม่มีใครตอบ',
  lead:      'ลูกค้าให้เบอร์',
  booked:    'นัดเข้าชม',
  fresh:     'เพิ่งตอบไปเมื่อกี้',
}
```

**กฎเหล็กของแบบนี้: สร้างจาก "ข้อความจริงในตาราง" เสมอ ห้ามยัดแถวลงตารางผลลัพธ์ตรง ๆ**
ถ้ายัดผลลัพธ์ลงไปเองก็แค่ทดสอบว่า INSERT ทำงาน ไม่ได้ทดสอบตรรกะอะไรเลย

**เรียก label สองจังหวะเวลา** ด้วย `p_now` คนละค่า — จังหวะแรกดูว่ารอบที่เพิ่งตอบ
ยังไม่ถูกตราหน้าว่าลูกค้าเงียบ จังหวะที่สองดูว่าพอเลย 24 ชม. แล้วมันอัปเกรดจริง
ฉาก `fresh` มีไว้เพื่อข้อนี้ข้อเดียว

**ฉากที่ต้องมีเสมอเมื่อมีลำดับความสำคัญ** — ฉากที่เงื่อนไขสองข้อจริงพร้อมกัน
เช่น `booked` ที่ลูกค้าให้เบอร์ด้วย ต้องได้ `booked` ไม่ใช่ `lead`
ถ้าไม่มีฉากแบบนี้ ลำดับความสำคัญจะสลับกันได้โดยไม่มีเทสต์ข้อไหนแดง

## 7. แบบ E — เดินทั้งเส้นจริง

ใช้เมื่อ: สิ่งที่จะพิสูจน์อยู่ "ระหว่าง" ชิ้นส่วน — ลายเซ็น, การยิงซ้ำ, คิว, โหมดเงา

**ยิงเข้า HTTP จริงด้วยลายเซ็นที่คำนวณจริง** ไม่ใช่เรียกฟังก์ชันภายใน
เพราะ bug ของชั้นนี้อยู่ที่ตรงกลาง เช่น อ่าน body ไปแล้วเลยเซ็นไม่ผ่าน

**อย่า `sleep` — ให้ `settle()` แทน**

```js
async function settle(timeout = 30000) {
  const until = Date.now() + timeout
  while (Date.now() < until) {
    const left = await one(`select count(*) from connect_private.webhook_log
                             where channel_key in ('line-test','fb-test')
                               and status in ('pending','processing')`)
    if (Number(left) === 0) return true
    await new Promise(r => setTimeout(r, 200))
  }
  return false
}
```

`sleep(2000)` จะช้าเกินจำเป็นตอนเครื่องว่าง และสั้นเกินไปตอนเครื่องช้า → เทสต์ผีหลอก
`settle()` รอ "จนกว่าคิวจะว่าง" ซึ่งเป็นเงื่อนไขจริงที่เรารอ

**ฉากที่มีค่าที่สุดของชั้นนี้**

- ยิง event เดิมซ้ำ → ต้องได้ข้อความเดียว (นับด้วย `event_id` ไม่ใช่เนื้อความ)
- ก้อนเกิน 1MB → ต้องไม่อ่านทั้งก้อน (413/503)
- ลายเซ็นผิด/ว่าง → ปฏิเสธ
- `destination` ไม่ใช่ของเรา → ปฏิเสธ
- ช่องทางที่ไม่มีในระบบ → 503
- **โหมดเงา: กดส่ง → 503 `shadow_mode`** และ worker **ขอ** งาน `generate` ได้แต่ **ไม่ขอ** งาน `send`
  (ตรวจที่ตัวเลือกงานที่ worker ขอ ไม่ใช่ตรวจหลังหยิบงานมาแล้ว — กันคนละชั้นกัน)

## 8. สูตรเพิ่มฉากใหม่

1. **เขียนฉากเป็นประโยคไทยก่อน** — "ลูกค้าส่งเบอร์ตอนตีสอง แล้วไม่มีใครตอบ 3 วัน"
2. **ถามว่าสิ่งที่จะพิสูจน์คืออะไร** — ตัวเลข? การตัดสินใจ? สิ่งที่ต้องไม่เกิด?
3. **เลือกชั้นที่ต่ำที่สุดจากตารางข้อ 2**
4. **หาค่าที่คาดไว้จากสเปก** (`PLAN.md` / `reference/` / คอมเมนต์ในไฟล์ SQL) **ก่อนรัน**
   เขียนค่าคาดลงไปก่อน แล้วค่อยรัน — ห้ามรันก่อนแล้วเอาผลมาเป็นค่าคาด
5. **รันแล้วแดง** → อ่านว่าคาดอะไรได้อะไร แล้วตัดสินว่าผิดที่ตรรกะหรือผิดที่ค่าคาด
   ถ้าค่าคาดมาจากสเปก ให้แก้ตรรกะเสมอ
6. **เพิ่มฉากตรงข้ามด้วย** — ฉากที่ต้องไม่เข้าเงื่อนไข (เบอร์บ้าน `021234567` ต้องไม่ถูกดึง)

## 10. ฉากพิเศษ: เทสต์ที่คุมกติกา ไม่ได้คุมผลลัพธ์

บางเรื่องกันด้วยการตรวจผลไม่ได้ ต้องตรวจ **ตัวโค้ด** แทน

```js
// tests/outcomes.test.mjs — กันไม่ให้มีนิยาม "รอบถาม" ซ้ำที่สอง
test('ไม่มีตรรกะ episode ซ้ำในไฟล์ SQL ของ Phase 9', async () => {
  const sqlText = await readFile('sql/013_conversation_outcomes.sql', 'utf8')
  assert.match(sqlText, /inbox\.reply_episodes\(/)           // ต้องอ่านจากของกลาง
  assert.doesNotMatch(sqlText, /lag\([^)]*sender_type/)      // ต้องไม่นิยามเอง
})
```

แบบเดียวกันนี้ใช้กับ Dockerfile ด้วย — ทุกโฟลเดอร์ที่ `server.mjs` import
ต้องมีบรรทัด `COPY` ใน Dockerfile ไม่งั้นคอนเทนเนอร์บูตไม่ขึ้น
(เคยพลาดสองครั้ง: `bots/` ตอน Phase 5 และ `reports/` ตอน Phase 7)

## 11. ฉากที่ยังไม่มี — ควรเพิ่มเมื่อถึงเวลา

| ฉาก | ทำไมยังไม่มี | เมื่อไหร่ต้องทำ |
|-----|--------------|-----------------|
| งานล้มแล้วลองใหม่ตามหลัง backoff | ต้องเดินเวลาในคิวให้ได้ | ก่อนเปิดใช้จริง |
| lease หมดอายุแล้วงานถูกหยิบซ้ำ | ต้องมี worker สองตัวพร้อมกัน | ก่อนขึ้นสองอินสแตนซ์ |
| cron ยิงจริงแล้ว insert job ลง outbox | pg_cron รันตามเวลาจริง | เรียกฟังก์ชันของ cron ตรง ๆ แทนได้เลย |
| ข้อความไทยยาวมาก/อีโมจิ/สติกเกอร์ | ยังไม่เจอปัญหา | ถ้าเจอ bug ตัดท่อนเมื่อไหร่ |
| หลายข้อความรัว ๆ ในวินาทีเดียว | ต้องยิงขนานเข้า HTTP | ก่อนเปิดใช้จริง |
